DEBUGGING // EXIT 137

Why does my local Docker container crash with `Exit Code 137 (OOMKilled)` during high-load tests?

Exit Code 137 indicates that the Linux Out-Of-Memory (OOM) killer terminated your container because it exceeded assigned memory limits or encountered an infinite event loop. To resolve:

  1. Increase your Docker Desktop engine RAM limit to at least 4GB/6GB in Settings -> Resources.
  2. Check for unclosed database pool connections or unbounded Node.js `EventEmitter` listeners.
  3. Run memory profiling using our diagnostics command:
$ docker stats --no-stream
$ node --inspect --max-old-space-size=4096 server.js

NETWORK ERRORS

Troubleshooting `WebSocket Connection Timeout` or `CORS Protocol Header Mismatch`

When connecting to real-time WebSocket endpoints (`ws://` or `wss://`), connection drops usually stem from reverse-proxy buffer timeouts or strict CORS configurations. Verify the following in your Nginx/Next.js config:

proxy_set_header Upgrade $http_upgrade;
proxy_set_header Connection "upgrade";
proxy_read_timeout 3600s;

Also ensure your client-side handshake includes valid `Authorization: Bearer ` tokens to pass rate-limiting firewall rules.

NODE & REACT ERRORS

Fixing `ModuleNotFoundError: Cannot find module` or Next.js Hydration Mismatch Errors

Hydration Mismatch occurs when the HTML generated during Next.js Server-Side Rendering (SSR) does not match the DOM tree rendered by React on the client side (typically due to `window` or `localStorage` checks inside component render loops).

To fix, wrap browser-dependent logic inside `useEffect()` hooks or use dynamic imports with `ssr: false`:

const ClientOnlyWidget = dynamic(() => import('./Widget'), { ssr: false });
DATABASE DEADLOCKS

Resolving PostgreSQL Sub-ms Query Deadlock on High Concurrency & Row Locking

Deadlocks occur when two concurrent transactions hold locks on separate database rows (`tx1` holds row A, `tx2` holds row B) and simultaneously attempt to acquire locks on the other transaction's rows.

To eliminate transaction lock conflicts under heavy concurrent workers:

  1. Always sort target primary key IDs in consistent alphabetical/numerical order before issuing multi-row `UPDATE` statements across workers.
  2. Use `FOR UPDATE SKIP LOCKED` when polling tasks or background queues to prevent workers from blocking each other:
SELECT id, payload FROM tasks WHERE status = 'pending' ORDER BY id FOR UPDATE SKIP LOCKED LIMIT 10;
